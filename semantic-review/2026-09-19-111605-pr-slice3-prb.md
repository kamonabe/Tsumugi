# Explicit frame stack for statement/block/loop execution (Slice 3 PR-b)

Converts the tree-walk evaluator's statement/block/loop Rust recursion into an explicit heap `Vec<Frame>` + cursor + `drive_body` driver loop in `src/eval.rs`. `exec_stmt` now returns `StmtStep` (`Val` / `Flow(FlowSignal)` / `Enter(Frame)`); compound statements build a child `Frame` and control flow (return/break/continue) unwinds the frame stack explicitly instead of the Rust stack. `eval_call`, `builtin.rs` callbacks, and `exec_program` all route function/program bodies through `drive_body`. Each pushed block/loop/try frame charges the deliberate §5.1 `continuation_frame` heap (96 + 32×locals), released on pop. The stated goal is unchanged observable behavior apart from that heap charge.

Watch for: (1) **confirmed** — errors raised while *advancing* a loop (condition re-eval on the 2nd+ iteration, end-of-iteration `count_step` fuel charge, per-iteration scope/heap/loop-var binding) bypass `handle_error` and escape an enclosing `try/catch` that the original caught; this is both a regression and a tree/VM parity break. (2) **confirmed** — out-of-loop `break`/`continue` error line numbers changed (now the offending statement's line, previously the call-site / enclosing-statement line), contradicting the doc's "観測挙動は不変" claim. (3) **likely** — a double `release_heap` on the catch-charge-failure path under-counts live heap.

**Verdict**: NEEDS_CHANGES

## High-level view

The frame-stack topology is faithful for the *normal* control-flow paths. Break pops the loop controller frame, continue leaves the controller and pops only the body block frame, return unwinds to the root frame, and per-iteration scopes plus the new continuation heap are released on pop/unwind. The `pending_step` mechanism reproduces the original end-of-iteration fuel timing (charge after a completed body, before the next condition/item, not on break), and the `for` frame's `_collection` field correctly preserves the iterated collection's live-heap lifetime for the loop's duration.

The correctness gap is in the *iteration-advance* path. `exec_stmt` runs each statement inside `drive_body`'s dispatch, where `Err` is routed through `handle_error` and can be caught by an enclosing `try`. But once a loop is running, the work that moves it to the next iteration — condition re-evaluation, the end-of-iteration `count_step`, and the per-iteration scope/heap/binding setup in `begin_loop_iteration` / `begin_for_iteration` — happens inside `advance_frame`, which uses `?` to return `Err` straight to `drive_body`, and `drive_body` sends `advance_frame` errors to `unwind_all` + `return Err`, never to `handle_error`. The original ran the whole loop inside `exec_scoped_block(try_body)`, so those same errors propagated out of `exec_block` and were caught by the `TryCatch` arm. The result is that a division-by-zero in a loop condition, or fuel exhaustion at an iteration boundary, is caught by the original tree-walk (and by the VM) but escapes uncaught in the new tree-walk.

The break/continue line-number change is a second observable divergence. Because the `Break`/`Continue` signals now carry the offending statement's own line, an out-of-loop break/continue reports that line, whereas the original reported the call-site line (in `eval_call`) or the enclosing top-level statement's line (in `exec_program` when the break sat inside a non-loop `if`). This actually converges tree-walk toward the VM, but it is not "unchanged" behavior and is undocumented as a change.

A narrow ledger bug sits in `handle_error`: if charging the catch frame's continuation heap fails, the try frame's already-released `heap_charge` is left in the frame and released a second time during `unwind_all`.

## Loop-advance errors escape an enclosing try (regression + tree/VM parity break)

This is the most serious finding. In the original, a `while`/`for` inside a `try` ran through `exec_scoped_block(try_body)`; any `Err` from the loop — including the condition `eval_expr`, the end-of-iteration `count_step`, or the per-iteration `env.push_scope`/binding — propagated out of `exec_block` and hit the `TryCatch` arm's `Err(e) =>` handler, building the error value and running the catch body.

In the new driver, only errors from `exec_stmt` go through `handle_error`:

```rust
match self.exec_stmt(stmt) {
    ...
    Err(e) => match self.handle_error(&mut frames, e) { ... }
}
```

Errors from `advance_frame` do not:

```rust
if frame.cursor >= frame.stmts.len() {
    match self.advance_frame(&mut frames) {
        Ok(()) => continue,
        Err(e) => {
            self.unwind_all(&mut frames);   // no handle_error — escapes any enclosing try
            return Err(e);
        }
    }
}
```

`advance_frame` raises via `?` in three places: `self.count_step(line)?` (end-of-iteration fuel), `self.eval_expr(condition, line)?` (while condition re-eval), and `self.begin_loop_iteration(...)?` / `self.begin_for_iteration(...)?` (per-iteration `push_scope`, `charge_heap`, and loop-var `env_set`). All of these are caught by the original and escape here.

Reproduced (`/tmp/t5.tsg`), condition raises on the 2nd evaluation inside a try:

```
let n = 2
try
  while (10 / (n - 1)) > 0
    n = n - 1
  end
catch e
  print("caught")
end
print("after")
```

Original tree-walk and VM both print `caught` / `after`. New tree-walk prints `3行目: ゼロ除算` — uncaught. Same outcome for end-of-iteration fuel exhaustion (`TSUMUGI_MAX_STEPS=3` on a counting `while` inside a try): original prints `caught fuel` / `after`, new tree-walk escapes with the step-limit error.

The fix is to route `advance_frame` errors through `handle_error` the same way `exec_stmt` errors are, then `continue` the driver loop when a catch frame was installed.

## First-vs-later-iteration asymmetry

A consequence of the split: the *first* condition evaluation and the *first* loop-variable binding run inside `exec_stmt` (the `Stmt::While` / `Stmt::For` arms), so a first-iteration failure is caught by `handle_error`. Every subsequent condition re-eval and binding runs in `advance_frame` and is not. So `while (1/0) > 0` inside a try is caught (first eval, in `exec_stmt`), but a condition that only divides by zero on the second evaluation is not. Whichever iteration raises decides whether the error is catchable — an observable inconsistency that disappears once the advance path also goes through `handle_error`.

## Break/continue error line numbers changed

`EvalResult::Break`/`Continue` and `FlowSignal::Break`/`Continue` now carry the offending statement's line. `exec_program`, `eval_call`, and the `builtin.rs` callback path all map that line into `break_outside_loop` / `continue_outside_loop`.

For `builtin.rs` this matches the original (`stmt.line()` for a bare top-level break equals the break's line). For `eval_call` it does not: the original used the call-site `line`. Reproduced with `fn f()\n break\nend\nf()` — original tree-walk reports line 4 (the `f()` call site), new tree-walk reports line 2 (the `break`). The VM reports line 2. For `exec_program`, a `break` inside a top-level `if` (no loop) reported the `if`'s line in the original (the top-level statement being iterated) and now reports the `break`'s own line; VM reports the `break`'s line.

So the change moves tree-walk onto the VM's line numbering — arguably a parity improvement — but it is a genuine change in observable error lines, and the design doc states the opposite ("観測挙動は不変 … ループ外 break/continue のエラー行を従来どおり保つ"). Either the doc should record this as an intended convergence, or the original lines should be preserved. No test covers this case, so it is currently silent.

## Control-flow topology: break, continue, return

Break, continue, and return unwind correctly on the frame stack. With the loop running as `[..., Loop(controller), Block(body), ...inner...]`, `unwind_flow` pops inner non-loop frames until it reaches the controller: `Break` pops the controller (ending the loop, no `count_step` — matching the original), `Continue` stops at and keeps the controller (having popped the body block frame in the `Some(false)` arm), so the next driver turn enters `advance_frame`, charges the pending step, and re-evaluates. `Return` pops everything down through the root frame and yields `EvalResult::Return(v)`. Each pop releases the frame's scope (`truncate_scopes(scope_base)`) and continuation heap, so per-iteration scope release holds on the break/continue/return paths.

## count_step timing via pending_step

The `pending_step` flag reproduces the original's end-of-iteration fuel charge. It is set true when a body iteration is pushed and consumed at the top of the next `advance_frame` before the condition/next-item check, so a completed body charges one step before the next iteration, break charges nothing (controller popped without re-entering `advance_frame`), and continue charges the step (controller retained, re-enters `advance_frame`). This matches the original `count_step` placement after the `match body_result?`. Empty-body loops still charge one step per iteration.

## for-loop _collection lifetime

`FrameKind::For` holds `_collection: Value` for the loop's duration. Since heap accounting lives on the `Rc<Tracked<T>>` backing (released by `Drop` when the last `Rc` falls), retaining the collection Value in the frame keeps its backing charged exactly as the original's `collection` local did, and it is released when the For frame is popped on every exit (normal completion, break, return, error via `handle_error`/`unwind_all`). Storing `items: Vec<Value>` and cloning per iteration (`items[*index].clone()`) adds only cheap `Rc` clones, no extra heap charge, so live-heap during the loop matches the original.

## try/catch scope handling and a double-release on catch-charge failure

`handle_error` finds the nearest `Try` frame (popping inner frames, releasing their scopes/heap), releases the try body's scope and continuation heap, then pushes the catch scope, charges `continuation_frame(1)`, binds the error var, and rewrites the frame into a `Scoped` catch frame. Ordering (release try scope before pushing catch scope) matches the original, and all error kinds are caught since `handle_error` triggers on any `exec_stmt` `Err` regardless of kind.

One defect: on the catch `charge_heap` failure branch,

```rust
self.env.push_scope();
let charge = continuation_frame(1);
if let Err(stop) = self.budget.charge_heap(charge, ExecutionPhase::Run) {
    self.env.truncate_scopes(top.scope_base);
    return Err(self.control_stop_to_error(stop, err_line));   // top.heap_charge still = old try charge
}
```

`top.heap_charge` was already released a few lines earlier (`self.budget.release_heap(top.heap_charge)`), but it is not zeroed here, so the subsequent `unwind_all` → `pop_frame` releases it again. `release` uses `saturating_sub`, so no panic, but `live_heap` under-counts by the try continuation size, corrupting the ledger baseline (relevant to REPL rollback). Set `top.heap_charge = 0` before returning on this branch.

## Frame leak paths

No leaks found on the paths that go through the driver: `pop_frame`, `unwind_flow`, `unwind_all`, and `handle_error` all release scope and heap. `begin_loop_iteration` / `begin_for_iteration` / `enter_*` release scope and heap on their own charge/bind failure before returning `Err`. The only accounting inconsistency is the double-release above.
