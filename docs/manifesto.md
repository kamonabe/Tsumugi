# Tsumugi Manifesto

最終更新: 2026-08-28

## この文書の位置づけ

このマニフェストは、Tsumugiが目指す方向と、設計上のトレードオフにおける優先順位を定める。
言語仕様やAPI仕様そのものではなく、判断に迷ったときに立ち返るための原則である。

ここに記載する内容は将来像を含み、現在の実装がすべての性質を保証していることを意味しない。
現在の保証範囲と未実装事項は、[設計ドキュメント](design.md)および[ロードマップ](roadmap.md)で管理する。

## 起源と次の段階

Tsumugiは、字句解析、構文解析、評価器、コンパイラ、仮想マシンなど、プログラミング言語処理系への理解を深めるための個人プロジェクトとして始まった。

その目的は今後も失われない。
一方、実装と監査を重ねる中で、言語の機能だけでなく、停止性、資源管理、意味論の一貫性、エラー後の状態回復が、実際の処理系にとって重要であることが明らかになった。

Tsumugiはこの学びをさらに発展させ、実運用を見据えた、制御可能な組み込みスクリプト言語の研究・開発プロジェクトへ進む。

## ミッション

> Tsumugiは、サーバーアプリケーションや業務システムに組み込み、ホストが明示的に付与した権限と実行予算の範囲内で、業務ルールや拡張ロジックを予測可能かつ監査可能に実行するためのスクリプト言語を目指す。

瞬間的な実行速度よりもホストの安定性を優先し、制御された負荷の中で処理を着実に進める。

> スクリプトを早く終わらせることより、ホストを止めないことを優先する。

## 原則

### 1. ホストの安定性を最優先する

スクリプトの待ち時間を短くするために、ホストの応答性や可用性を犠牲にしない。
平均的な軽さだけでなく、負荷の最悪値を制御できることを重視する。

過負荷時にはCPUやメモリを使い尽くすまで走り続けるのではなく、実行を一時停止、延期、キャンセル、または制御されたエラーとして終了できるようにする。

### 2. 権限はホストが明示的に付与する

スクリプトは、ホストから与えられていない資源や操作へ暗黙にアクセスできないことを目指す。
filesystem、環境変数、時刻、標準入出力、外部サービス、業務操作などの外部効果は、実行単位のcapabilityとして明示的に提供する。

利便性のためにambient authorityを既定で公開するより、必要な能力だけをdeny-by-defaultで付与する。

### 3. すべての実行に予算を設ける

命令またはfuel、メモリ、実行時間、入出力量、外部呼び出しなど、スクリプトが消費できる資源をホストが制御できるようにする。

個々の実行が上限内でも、同時実行の合計によってホストが過負荷になる可能性がある。
そのため、実行単位の予算だけでなく、エンジン全体の同時実行数と総資源消費も制御対象とする。

言語内の制限は、必要に応じてプロセス、コンテナ、cgroupなどのOSレベルの制限と組み合わせる。

### 4. 負荷を平準化し、着実に進める

短時間に資源を集中させる実行だけでなく、ホストへ定期的に制御を返し、低い負荷で長時間かけて進める実行を選べるようにする。

実行量を小さな単位へ分割し、yield、backpressure、キャンセルを扱える構造を目指す。
対話処理、バックグラウンド処理、保守処理など、用途ごとに待ち時間と資源使用量のバランスを選択できるようにする。

### 5. 最速より予測可能性を優先する

同じ言語version、スクリプト、入力、権限、外部応答から、同じ結果と同じ副作用順序が得られることを目指す。

最適化によって意味論、評価順、エラー、資源消費が実行backendごとに変わることを許容しない。
性能は計測して改善するが、最大スループットのために説明可能性を犠牲にしない。

### 6. 失敗を制御可能な結果にする

成功だけでなく、予算超過、権限拒否、キャンセル、構文エラー、実行時エラー、ホスト機能の失敗も正式な実行結果として扱う。

スクリプトの失敗によって、ホストプロセスがpanic、abort、または意図せずexitしないことを目指す。
予算超過をスクリプト側で捕捉して無制限に実行を再開するなど、ホストの制限を回避できる経路を作らない。

Tsumugiが目指す「確実な実行」とは、任意のスクリプトの成功を保証することではない。
ホストを不安定にせず、完了、停止、または失敗のいずれかを観測可能な形で扱えることを意味する。

### 7. 実行を観測・監査可能にする

どのスクリプトが、どの言語version、入力、権限、予算で実行され、どの外部操作を行い、どのように終了したかを、ホストが構造化して記録できるようにする。

長時間実行では、進捗、資源消費、停止理由を外部から確認できることを重視する。
人が付ききりで監視しなくても結果を確認できる実行基盤を目指す。

監査性を理由に秘密情報や個人情報を無制限に記録せず、redactionと記録範囲をホストが制御できるようにする。

### 8. 小さく理解可能な中核を保つ

機能数を増やすことより、処理系全体を理解、検証、テストできることを優先する。
純粋な計算や基本データ操作は言語中核に置き、filesystem、network、database、メール、業務操作などの外部効果は、原則としてホスト境界の後ろに置く。

HTTPクライアントやDBドライバの選択を言語中核へ固定せず、ホストアプリケーションが用途に応じて提供する。

### 9. 学びと検証を継続する

Tsumugiは実運用を見据えても、処理系を理解するためのプロジェクトであり続ける。
複雑な最適化や抽象化を導入する場合は、動機、保証、トレードオフを文書化し、再現可能なテストと計測で裏付ける。

実装だけでなく、失敗事例と未解決事項も記録し、設計判断を後から検証できる状態を保つ。

## トレードオフの優先順位

設計上の要求が衝突する場合は、原則として次を優先する。

| 優先するもの | 優先しないもの |
|---|---|
| ホストの可用性 | スクリプト単体の最短実行時間 |
| 制御可能な最悪時負荷 | 平均ベンチマークだけの速さ |
| 明示的なcapability | ambient authorityによる利便性 |
| 一貫した意味論 | backend固有の最適化 |
| 構造化された停止・失敗 | best-effortでの実行継続 |
| 小さく監査可能な中核 | 広範な組み込み機能 |
| 再現可能な検証 | 根拠のない性能・安全性の主張 |

## 目指さないもの

Tsumugiは、少なくとも現在の方向性では、次のものを目指さない。

- 最大の実行速度やスループットを競う言語
- Tsumugiだけでアプリケーション全体を構築する汎用言語
- OSやシェルの代替
- 単体で敵対的コードを完全に隔離するsecurity sandbox
- 任意のスクリプトが必ず成功するという保証
- あらゆる外部サービスを内包する巨大な標準ライブラリ
- alpha段階における言語仕様、組み込みAPI、CLIの完全な後方互換性

敵対的コードを扱う場合は、Tsumugiの制限だけに依存せず、別プロセス、コンテナ、最小権限、CPU・メモリ・実行時間制限などを併用する。

## 現在地

現在のTsumugiには、ステップ上限、コレクションサイズ上限、call・AST・import深度制限、filesystemと環境変数のallow-list、構造化エラー、ツリーウォーク版とVM版の差分テストがある。
これらは新しい方向性の土台だが、完成した組み込み実行基盤ではない。

特に、次の項目は今後の設計・実装対象である。

- 安定した高水準の組み込みAPI
- 実行単位のdeny-by-default capability
- fuel、総メモリ、wall-clock、入出力を含む包括的な実行予算
- エンジン全体の同時実行制御とbackpressure
- cooperative execution、キャンセル、一時停止・再開
- 外部入力をホストから注入できる決定的な実行境界
- 単一の規範意味論とbackend間の一致
- 実行時の構造化audit event
- 資源制約下で安全に実行できるテスト・検証手順

現在の環境変数ベースの制限はdefense-in-depthであり、未設定時に全アクセスを許可する経路もある。
マニフェストに記載したcapability modelや包括的な実行予算を、現行機能がすでに満たしているとはみなさない。
