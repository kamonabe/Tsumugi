# Tsumugi — ドキュメント運用ガイド

このガイドは「どの情報をどのドキュメントに書くか」を定める。仕様駆動開発であり、設計正本（spec doc）が実装の正本である。各ドキュメントの役割を固定することで、情報の重複・drift・置き場所の誤りを防ぐ。

AI エージェント・人間のどちらも、新しい情報を書く前にまず「その情報はどの種別か」を判断し、下表の owning document へ書くこと。

## 大原則

- **仕様駆動開発であり、spec doc が実装の正本。** 実装と spec が食い違う場合は spec を正とし、spec を更新してから実装を直す。
- **ロードマップは spec を要約しない。進捗だけを追う。** 機能の詳細・採用/不採用の理由は spec に書く。ロードマップに detail を書き始めたら、それは置き場所の誤りである。
- **状態の正本は粒度ごとに 1 箇所だけ。** 項目（REV/AUD/Phase 残など）の状態（✅/🟡/⬜）は [ロードマップ](roadmap.md) の「ステータス一覧」表、実装スライスの状態は [`slices.toml`](slices.toml) が唯一の正本である。spec の実装状態（目標仕様に対する逸脱・未実装範囲）は各 spec の **逸脱一覧**（下記「逸脱一覧の持ち方」）が唯一の正本である。他の節・表・ドキュメントは状態を再掲せず、これらを参照する。同じ事項の状態を複数箇所に書くと食い違いの原因になる。

## 逸脱一覧の持ち方

各 spec の本文（章立てされた仕様）は **到達目標の確定仕様**であり、現在の実装状態ではない。目標と現状を同じ本文に混ぜると、正本が目標なのか現状なのか分からなくなる。そこで次のように置き場所を 1 つずつに分ける。

- **目標** = spec 本文の各章。実装状態を書かない。
- **現状** = spec ごとに **逸脱一覧を 1 つだけ**持つ。目標仕様に対する現在の逸脱と未実装範囲を表形式で記録する（逸脱と未実装範囲は 1 表でも、明確に分けた 2 表でもよい）。表は現在の逸脱と未実装範囲だけを持ち、**解消した行は削除する**（どのスライスで解消したかはスライス小節と git 履歴に任せる）。列は最低限、逸脱は「逸脱内容 / 対象の節(§) / 発生スライス」、未実装範囲は「未実装範囲 / 対象の節(§)」を持つ（1 表にまとめる場合は逸脱の列に揃える）。解消を表の中で表す「解消スライス」「状態（未解消/解消済み）」の列は置かない。spec 冒頭の設計ステータス段落がこの役割を担う。
- **経緯** = 各実装スライス小節。そのスライスを実装した時点の記録として凍結する。

**状態（どの逸脱・未実装範囲が今残っているか）の正本はこの逸脱一覧だけである。** 表に行があることが「残っている」ことを表す。スライス小節は状態を再掲しない（上記「状態の正本は粒度ごとに 1 箇所だけ」と同じ原則）。逸脱一覧は「今の実装がどう振る舞うか」を書くので、記述だけで判断できない項目はコードやテストで事実を確かめてから書く。

> **移行中:** [`execution-control.md`](execution-control.md) は逸脱一覧をまだ持たない。次に done を出す実装 PR で寄せる。

## スライス小節は凍結された時点の記録

実装スライス小節は、そのスライスを実装した時点の記録であり、**後から書き換えない**。後続スライスが前のスライス小節の状態注記を遡って直す運用はやめる（この運用があると、直し忘れで古い記述が残り、状態が複数箇所に散る）。

- A-1 小節の「redaction 本体が未実装」といった記述は誤りではなく、A-1 時点では正しかった時点の記録である。それが時点の記録だと読み手（AI・人間）に伝わるよう、spec の実装slice章の冒頭に一度だけ「各スライス小節は実装時点の記録。現在の逸脱・未実装範囲は逸脱一覧を見る」と書き、[`CLAUDE.md`](../CLAUDE.md) にも同じ読み方を一文で置く。
- 現在の状態は spec 本文でもスライス小節でもなく、**逸脱一覧だけ**が持つ。解消した逸脱・未実装範囲は逸脱一覧から行を削除する（スライス小節の記述は直さない）。

## 用語

| 用語 | 意味 | 例 |
|---|---|---|
| Phase | 目標アーキテクチャへの移行段階（0〜7） | Phase 6 実行時監査 |
| 項目 | ロードマップ「ステータス一覧」の 1 行 | REV-015、AUD-020、Phase 6 残 |
| spec の slice | 各 spec の「実装slice」章にある粗い段階 | determinism Slice 5、E9、C12 |
| **実装スライス** | 1 実装 PR で完了させる単位。spec の slice を実装可能な大きさに切ったもの | A-1、B-2、R-1a、F-1 |

以下、単に「スライス」と書いた場合は実装スライスを指す。

## ロードマップと spec の責務分離

ロードマップは「今どのフェーズにいて、次に何をやるか」と「各項目の状態」だけを管理する。具体的には次を持つ。

- 現在地（フェーズ・現在のスライス・次のスライス）を数行で。直近完了は 1 件だけ書き、それ以前の履歴は持たない（履歴は spec の実装スライス小節と git log にある）。
- マイルストーン（Phase 0〜7）の目的・設計正本 link・状態・完了 gate。
- 項目の状態の唯一の正本である「ステータス一覧」表（ID・一行概要・状態・owning spec）。項目の状態は配下スライスの状態から判断する。
- 着手順は [`slices.toml`](slices.toml) の `order` を正とし、ロードマップは link だけを持つ。

> **移行中:** ロードマップの「現在地」「着手順」はまだ上記の形に縮小していない（直近完了の履歴と着手順の本文が残っている）。縮小は別 PR で行う。それまでの間も、次に何をやるかは [`slices.toml`](slices.toml) を正とする。

ロードマップは次を持たない。これらは spec doc の役割である。

- 機能の実装詳細（型名・PR 単位の変更内容・コミット単位の説明）。
- 設計判断の根拠（採用理由・却下した案・トレードオフ）。
- 受入基準の本文（gate の名前は参照してよいが、条件の全文は spec に置く）。

新しく仕様を書くときは、まず上表で owning document を特定し、そのドキュメントの既存の節構成・prose スタイルに合わせて追記する。ロードマップ側は「状態」と「spec への link」だけを更新する。

## 実装スライスの運用

ここでいう **ループ** とは、エージェントが「`ready` のスライスを 1 つ選ぶ → spec を読んで実装する → 実装 PR を出す → 人間のマージを待つ」を繰り返す開発の進め方を指す。定時実行でも対話でも、規則は本節に従う。定時実行での 1 回分の実行手順（実行モード・判断待ちの出し方・マージの条件）は [開発ループ手順書](loop-runbook.md) に置く。

### 書き手と承認

- [`slices.toml`](slices.toml) を書き換えるのはエージェント（Claude / Kiro）だけである。人間は直接編集しない。
- 書き換えは必ず PR の中で行い、main へ直接 push しない。
- **その PR がマージされた時点で状態が確定する（マージ = 承認）。** エージェントは自分で承認できず、人間はファイルを編集しない。承認として扱うのは次のどちらかだけである。
  - リポジトリ所有者（kamonabe）によるマージ
  - kamonabe がその PR に書いた承認コメント（`承認: マージしてください`）を受けて、エージェントが [開発ループ手順書](loop-runbook.md)「マージしてよい条件」を満たしたうえで行うマージ
- ループが同時に開いておける PR は、`loop:design` 1 本・`loop:impl` 1 本までとする。

| 遷移 | 行う PR | PR に含めるもの |
|---|---|---|
| （新規追加）→ todo | 設計 PR または状態整理 PR | `slices.toml` へのエントリ追加 |
| todo → ready | 設計 PR | spec の実装スライス小節の追加・更新、`status` の変更、`spec`・`acceptance`・`design_pr` の記入 |
| ready → done | 実装 PR | 実装・テスト、spec の逸脱一覧の更新（新しい逸脱・未実装範囲の追加、解消した行の削除）、`status` の変更、`impl_pr` の記入 |
| ready → todo（差し戻しの確定） | 設計 PR | spec の修正、`issues` への追記、needs-design issue のクローズ |
| → blocked / blocked → todo | 状態整理 PR | `blocked_reason` の記入・削除 |

### 実効状態

main 上の `status` には承認済みの状態だけを書く。設計中・レビュー待ち・差し戻し中といった一時的な状態はファイルに書かず、GitHub 上の PR と issue から導出する。

| main 上の status | GitHub 上の状況 | 実効状態 |
|---|---|---|
| todo | なし | 未設計 |
| todo | オープンな設計 PR あり | 設計レビュー待ち |
| ready | なし | **着手可能** |
| ready | オープンな実装 PR あり | 実装レビュー待ち |
| ready | オープンな `needs-design` issue あり | 差し戻し中（着手しない） |
| done | — | 完了 |
| blocked | — | 着手不可 |

PR・issue とスライスは次の命名で紐付ける。

- ブランチ: `docs/<スライスID>`（設計 PR）、`feat/<スライスID>` または `fix/<スライスID>`（実装 PR）。prefix はワークスペース共通の Git 運用ルールに合わせる
- ラベル: `loop:design`、`loop:impl`、`needs-design`
- issue タイトル: `[needs-design] <スライスID>: <止まった理由の要約>`

### ready の条件（Definition of Ready）

設計 PR で `ready` にしてよいのは、次をすべて満たすときだけである。

1. `spec.section` が `spec.doc` に見出しとして存在し、その小節に実装範囲・範囲外（逸脱）・受入基準 ID が書かれている。
2. `acceptance` が空でない。
3. `depends_on` のスライスがすべて `done` である。

本ガイド導入前に完了したスライス（`done`）は、受入基準 ID が未採番でも登録してよい。

### done の条件（Definition of Done）

実装 PR で `ready` → `done` にするとき、次をすべて満たす。

1. 実装とテストが揃い、受入基準を満たす。
2. **done にする実装 PR で、その spec の逸脱一覧に新しい逸脱・未実装範囲を追加し、解消した行を削除する**（「逸脱一覧の持ち方」）。状態の正本は逸脱一覧なので、ここを更新しないと現状が古いままになる。
3. 過去のスライス小節は書き換えない（「スライス小節は凍結された時点の記録」）。現在の状態は逸脱一覧の側だけで更新する。
4. `slices.toml` の `status` を `done` にし、`impl_pr` を記入する。

### 実装中に止まる場合

実装中に spec に書かれていない判断が必要になり、その判断が実装範囲・公開 API・データ構造・言語挙動に影響する場合は、推測で埋めずに実装を止める。止めたときは `needs-design` issue を立て、どこで止まったか・考えられる選択肢・推奨案を書き、[開発ループ手順書](loop-runbook.md)「判断待ちの扱い」に従って Slack で kamonabe の判断を求める。設計中に同じ種類の判断が必要になった場合も同様に扱う（このときは issue ではなく設計 PR に書く）。

止めるほどではない小さな判断は実装 PR 本文の「仕様外で判断した点」に必ず列挙する（[PR テンプレート](../.github/pull_request_template.md)）。レビューでその判断が誤りと分かった場合は、レビューコメントに `[判断NG]` を付ける。
